# SCP Deployment Definitions (CloudHub-Vendored)

This tree vendors the SCP Helm Deployment Pipeline definitions from
`SymphonyFS/scripts` so **CloudHub Native deployments have zero dependency on
that repository**. Everything a deployment needs lives in this repo.

## Layout

```
scp/
├── apps/<app>/                  # Per-app helmfile deployment template
│   └── helmfile.yaml            # Sanitized SCP helmfile (see below)
└── templated-overrides/         # Per-app value overrides + raw YAML charts
    ├── <app>/*.gotmpl           # App-specific override templates
    └── raw-yaml-charts/         # Local charts (trident-backend, tailscale-on-scp, ...)
```

## Sanitization applied during vendoring

The upstream helmfiles used credentials and cross-repo references that would
recreate the dependency this tree removes. They were rewritten as follows:

1. **`git::.../SymphonyFS/scripts.git@/templated-overrides/...` →
   `../../templated-overrides/...`** — overrides resolve locally.
2. **`git::.../SymphonySensa/helm.git@/charts/...params-*.yaml` →
   `values/params-*.yaml`** — per-instance values files are generated by the
   CloudHub Deployment Portal next to the instance helmfile.
3. **`{{ fetchSecretValue "ref+op://..." }}` → `{{ env "CLOUDHUB_<KEY>" }}`** —
   secrets come from the platform Azure Key Vault (`cloudhub-deploy-vault`)
   injected as environment variables by the deploy workflow, never from
   1Password.
4. **Relative chart paths** adjusted for this repo's layout
   (`../../../templated-overrides` → `../../templated-overrides`).

## How deployments run (CloudHub Native)

1. A deployment request is created in the CloudHub Deployment Portal and goes
   through the **approval workflow** (`PENDING` → approved by a second admin).
2. On approval, the backend renders `apps/<app>/<instance>/helmfile.yaml` +
   `values.generated.yaml` (chart references point at the local vendored
   charts above) and commits them to `main`.
3. The `deploy-helmfile.yml` GitHub Actions workflow authenticates to the
   target AKS cluster (OIDC), runs pre-flight validation, executes
   `helm upgrade --install --atomic`, runs Helm tests and 4-point health
   verification, and uploads an installation report.
4. Production instances additionally gate on the GitHub `production`
   environment (second approval layer).
